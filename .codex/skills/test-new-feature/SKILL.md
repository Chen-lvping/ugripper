# test-new-feature

## 固定执行顺序

1. 先阅读 `docs/agent/overview.md`，再开始设计方案。
2. 输出“实现计划 + 影响文件列表 + 文档同步计划”，进入等待开工状态。
3. 只有收到用户**明确的确认并开始指令**后，才开始改代码与文档。
4. 代码与文档改完后，仅围绕新增功能执行局部测试或定向验证。
5. 测试完成后，再给最终汇报。

## 计划反馈阶段处理（强约束）

1. 给出计划后，默认状态为 `WAIT_FOR_EXPLICIT_START`。
2. 在该状态下，用户提出修改意见、补充约束、质疑、讨论细节时，只能更新计划并继续等待，**不得**开始任何代码或文档落地修改。
3. 仅以下类型指令可解除等待状态并开工：`确认并开始`、`开始实现`、`按该计划执行`、`可以开改了`（或同等明确语义）。
4. 若用户表达模糊（如“先这样”“看起来可以”），先追问一次“是否现在开始实现”，未得到明确开工指令前保持等待。

## 代码修改规则

1. 修改范围保持最小化，只实现当前 feature，避免顺手重构。
2. 落地修改时，优先使用 heredoc 或等价的批量补丁方式，避免零碎手改。
3. 所有改动完成后，汇总可追踪 diff（按文件说明改动点）。

## 文档同步规则（docs）

1. 每次 feature 修改后，必须同步创建或维护相关文档。
2. 默认至少检查并更新 `docs/agent/overview.md` 中受影响的条目。
3. 当流程、模块边界、运行时架构变化时，统一更新 `docs/agent/overview.md` 对应章节。
4. 每次 feature 修改后，都要维护 `docs/CHANGELOG.md`，内容聚焦“软件功能改动”，避免写构建过程流水；条目尽量简洁。
5. 仅在确有新增知识且无法放入现有文档时，新增文档；避免文档碎片化。

## 局部测试与验证规则（新增）

1. 测试目标仅聚焦新增功能及其直接影响路径，不做全量回归、编译、打包、发布验证。
2. 优先选择最靠近改动点的低成本验证：定向命令、局部单测、模块级脚本、语法检查、dry-run、日志核对等。
3. 若用户指定测试方式，以用户指示为准；未指定时，自动选择最小充分验证集。
4. 默认不执行构建、打包、烧录、升级包导入、服务重启等高成本或有副作用步骤；若确有必要，需先获得用户明确同意。
5. 若缺少环境、依赖、设备或样本数据导致无法完成局部测试，必须明确说明阻塞点，并给出可执行的手动验证步骤。
6. 除非用户后续明确追加要求，否则**不得**调用 `auto-release-deb`，**不得**修改 `build_deb.sh` 与 `usb_updater_build.sh` 版本号。

## 验收与检查默认策略

1. 默认执行轻量、局部、低副作用检查，不主动跑全量测试。
2. 只有用户明确要求“全量测试 / 回归 / 编译验证”时，才扩大检查范围。
3. 若局部测试失败，需停止继续扩展验证，汇报失败命令、关键现象和初步判断，等待用户指示。

## 输出格式要求

最终回复按以下顺序输出：

1. 代码改动摘要（按文件）。
2. 文档改动摘要（按文件）。
3. 已执行的局部测试/定向验证（命令、结果、结论）。
4. 未执行的测试与跳过原因。
5. 建议的手动验收步骤。
