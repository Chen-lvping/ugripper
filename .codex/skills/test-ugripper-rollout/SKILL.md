# test-ugripper-rollout

## 适用场景

当用户需求属于以下任一类时，优先使用本 skill：

- 重新阅读 `pp_main` 合并后 `ugripper` 测试文档并确认现状
- 梳理“当前还需要完成哪些测试目标”
- 压缩测试推进清单、按项排优先级
- 回填板端测试结果到正式文档
- 补 `pp_main/test`、`pp_main/test/scripts`、归档测试计划相关测试资产
- 讨论是否需要重新打包、重新上板、重新跑某轮验证

以下场景不应优先使用本 skill：

- 纯重构：改用 `refactor-ugripper`
- 纯新增功能：改用 `add-feature` 或 `test-new-feature`
- 只读故障排查：改用 `debug-ugripper`

## 固定执行顺序

1. 先阅读以下文档建立上下文：
   - `docs/archive/2026-refactor-history/ppmain-ugripper-test-plan.md`
   - `docs/REFACTOR_LOG.md`
   - `docs/CHANGELOG.md`
2. 若用户问题涉及并仓背景、运行时边界或上一阶段重构约束，继续补读：
   - `docs/archive/2026-refactor-history/standalone-merge-plan.md`
   - `docs/ugripper-refactor-architecture.md`
   - `docs/archive/2026-refactor-history/reference-aligned-refactor-next-steps.md`
3. 若问题涉及“最近一次是否已验证 / 板端到底测到哪一步”，继续检查：
   - `tmp/board_results/`
   - `pp_main/test/scripts/`
   - `pp_main/test/`
4. 先按以下三种状态复盘，不要直接下结论：
   - `已落地`
   - `已接线`
   - `已重跑验证`
5. 输出“当前状态 + 待完成目标 + 风险边界 + 建议执行顺序”，进入等待开工状态。
6. 只有收到用户**明确的确认并开始指令**后，才开始修改测试文档、补测试代码、补脚本或执行新的验证。
7. 落地后，最少同步更新：
   - `docs/archive/2026-refactor-history/ppmain-ugripper-test-plan.md`
   - `docs/REFACTOR_LOG.md`
8. 若本轮有板端或容器实测结果，必须把结果目录、汇总 JSON 路径和“已证明 / 尚不能单独证明”的边界写清楚。

## 阶段识别规则

默认按 `docs/archive/2026-refactor-history/ppmain-ugripper-test-plan.md` 的 `T1-T16` 与 `L0-L4` 识别当前工作所处阶段：

- `T1-T5`
  - 判定标准、观测点、日志链路
- `T6-T9`
  - analyzer / 离线检查器落地
- `T10-T12`
  - 规则下沉到 `host-only`
- `T13-T15`
  - 板端标准脚本化
- `T16`
  - 发版前回归与统一报告

若用户只问“现在还差什么”，优先从以下 4 个角度回答：

1. 哪些已经有测试资产
2. 哪些已经在板端重跑过
3. 哪些仍缺强覆盖
4. 下一步最该做哪一项

## 计划反馈阶段处理（强约束）

1. 给出计划或压缩清单后，默认状态为 `WAIT_FOR_EXPLICIT_START`。
2. 在该状态下，用户提出修改意见、补充约束、重新排序、要求先解释概念时，只能更新计划，**不得**直接修改代码或文档。
3. 仅以下类型指令可解除等待状态并开工：`开始`、`开始做`、`按这个推进`、`把它写进文档`、`补测试`、`去上板验证`（或同等明确语义）。
4. 若用户表达模糊，先确认本轮是：
   - 只整理现状
   - 修改文档
   - 补测试资产
   - 执行验证

## 实施规则

### 1. 先压缩，再展开

每轮推进先给“压缩版推进清单”，默认格式：

1. 当前已完成
2. 当前未完成
3. 这轮只做什么
4. 做完如何验证

只有在用户要求细化时，才展开到 `T1-T16` 明细。

### 2. 默认先核对现状，不重复劳动

在以下场景默认先做只读核对：

- 用户说“不是已经测过了吗”
- 用户说“当前代码就是这版包”
- 用户问“还要不要重新打包 / 重新上板”

默认先检查：

- 文档里最近一次重跑记录
- `tmp/board_results/` 是否已有对应结果
- 当前板端已知版本号与本地测试结论是否一致

不要在没有证据的情况下默认“必须重新出包”或“必须重跑”。

### 3. 文档更新规则

涉及测试推进时，文档更新默认遵循：

- 测试计划文档写“正式状态、覆盖边界、待完成项”
- `REFACTOR_LOG` 写“本轮做了什么、验证了什么、后续还差什么”
- 若只是补追溯信息，优先更新上述两份，不要滥加新文档

回填板端结果时，至少写清：

- 日期
- 板端包版本
- 执行的脚本
- 结果目录
- 汇总 JSON
- `ok / validation_reason`
- 本轮已证明什么
- 本轮尚不能单独证明什么

### 4. 测试推进优先级规则

默认优先级：

1. 先补 `host-only` 高价值规则
2. 再补 analyzer 口径缺口
3. 再补板端标准脚本入口
4. 最后做更重的长时 / 高压 / release gate 收口

如果用户问“下一步最合适做什么”，默认优先看：

- `T12`
- `T10/T11`
- `T15`
- `T16`

### 5. 板端验证边界

若本轮涉及板端验证，默认区分：

- `已验证当前板端安装包`
- `已验证当前本地代码重新打包后的新包`

只有在能够证明“本地代码与板端已安装包不一致，且本轮目标是验证本地新改动”时，才建议重新打包。

### 6. 最小验证规则

每次修改后，只执行与本轮目标匹配的最小验证：

- 文档更新：核对路径、日期、结果文件和结论一致
- host-only 规则：跑对应 `ctest` / Python fixture
- 板端脚本：跑对应单条入口，不默认扩大到整套
- 回填结论：核对 `tmp/board_results` 与文档一致

## 默认输出格式

当用户要求“重新阅读测试文档，确认目标与现状”时，默认输出顺序：

1. 当前状态
2. 还差什么
3. 最该先做什么

当用户要求“压缩一下按项推进”时，默认输出顺序：

1. 已完成项
2. 待完成项
3. 下一步

当用户要求“写进文档 / 记入日志”时，默认同步说明：

1. 写入了哪份文档
2. 写入了什么类型的信息
3. 这次更新不意味着什么边界被自动关闭
