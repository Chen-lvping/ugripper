# git-commit

## 提交信息标准

1. 使用 `Conventional Commits`。
2. 默认格式：`type(scope): subject`
3. 默认使用英文提交信息；除非用户明确要求其他语言，否则 `type`、`scope`、`subject` 都使用英文。
4. `subject` 必须使用简洁英文，明确本次功能/修复主题，不写空泛描述。
5. 无明确 scope 时可省略为 `type: subject`。

## 常用 type 选择

- `feat`：新增功能
- `fix`：修复问题
- `refactor`：重构但不改外部行为
- `docs`：纯文档修改
- `test`：测试相关
- `chore`：杂项维护、脚本、配置、构建辅助

## 提交范围规则

1. 若用户明确指定提交某个功能、模块或文件范围，只提交该范围及其直接相关改动。
2. 功能、修复或测试相关的 `docs` 修改默认跟随对应提交，包括 `CHANGELOG`、维护说明、测试计划、验证结果与日志回填；不要仅因文件位于 `docs/` 就拆成独立 `docs` 或 `test` 提交。
3. 提交颗粒度不要过细，优先按“一个完整功能 / 一个完整修复 / 一个明确范围”组织，而不是按文件碎片化拆分。
4. 若用户未指定范围，默认提交当前全部更改。
5. 若用户未指定范围，且当前改动很多、明显不属于同一类、或混有多个独立主题，先二次确认再提交，不能擅自合并成一个提交。

## 伴随改动归属规则

1. `build_deb.sh`、`scripts/build_arm_deb_in_pp_arm_dev.sh` 等文件中的版本号更新，默认不拆成独立 `chore(release)` 提交；本批存在功能或修复提交时，将版本更新纳入最后一个相关提交。
2. `graphify-out/` 下由 `graphify update .` 生成的图谱、报告与标签更新，不列为独立可提交项，也不创建独立 `chore(graphify)` 提交；将它们纳入本批最后一个提交。
3. 多个提交主题共享同一文档或源码文件时，使用按 hunk 暂存，将相关内容分配给对应功能；无法可靠拆分时，优先合并相近主题，避免制造纯文档或纯生成物提交。
4. 只有当文档、版本更新或 graphify 产物本身就是用户明确指定的唯一提交范围时，才允许作为独立提交处理。

## 执行顺序

1. 先执行 `git status --short` 了解改动范围。
2. 如用户指定了范围，先筛出该范围内的文件，并检查是否混入无关修改。
3. 判断本次提交主题，并拟定符合 `Conventional Commits` 的提交信息。
4. 若存在版本号、关联文档或 `graphify-out/` 更新，先按上述伴随规则分配到对应提交。
5. 若需要二次确认，先给出建议的提交划分，不直接提交。
6. 无需确认时，执行 `git add` 与 `git commit`。
7. 提交后返回提交信息、提交 hash 和本次纳入的主要范围。

## 二次确认触发条件

满足任一条件时先确认：

- 用户未指定范围，但工作区同时存在多个明显独立功能/修复。
- 改动跨多个模块，且无法合理归为同一主题。
- 工作区里同时存在实验文件、临时文件、资产文件和代码改动，无法确定是否都应纳入。

## 输出要求

提交前若需要确认，输出：

1. 当前改动的主题归类。
2. 建议的提交划分。
3. 每个建议提交对应的 `Conventional Commits` 标题。
4. 明确最后一个提交将随附的版本更新、关联文档与 graphify 产物，不把这些内容单独列为提交项。

提交完成后，输出：

1. 实际提交标题。
2. 提交 hash。
3. 本次提交范围摘要。
4. 若有未提交改动，明确说明剩余范围。
